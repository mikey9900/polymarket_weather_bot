The two Oct 7 NYC temperature contracts specify a Weather Underground Daily Observations fallback if NOAA data is unavailable by 11:59 p.m. ET the following day, then the lowest bracket if neither source has data. They become eligible for resolution when the first following-date observation appears or at that cutoff. The contracts allow an exceptional correction window of up to seven calendar days for clearly erroneous source data; routine revisions to readings count only until the first following-date datapoint appears. **Rules must be read per event:** [Amsterdam Oct 7](https://gamma-api.polymarket.com/events?slug=highest-temperature-in-amsterdam-on-october-7-2026) uses the NOAA WRH `Temp` column at Schiphol (EHAM) in whole °C but does not specify the NYC hourly-only filter.

NOAA's [WRH Time Series Viewer help](https://www.weather.gov/wrh/timeseries?site=klga) says its displayed data are preliminary. The default table shows all reports; selecting **Show Only Hourly Data** selects timestamps at minutes 51–59 for NWS/FAA platforms, including special observations, and minutes 56–04 for other platforms. It also says the download-data feature is currently unavailable. A bot using every METAR, a daily climate high, or a generic NWS API 24-hour extreme could therefore produce a different answer from the specified table. This source match is an operational requirement, not a proven trading edge.

The NWS [CLI product description](https://www.weather.gov/box/product_descriptions) says the full previous-day report is issued between 12:30 and 5:00 a.m. local time; an afternoon report covers the current day. [NWS's climate-day explanation](https://www.weather.gov/fwd/understandf6) specifies 00:00–23:59 local standard time, equivalent to 01:00–00:59 during daylight saving time. The [current KNYC CLI product](https://forecast.weather.gov/product.php?site=NWS&product=CLI&issuedby=NYC) exposes `PRECIPITATION (IN)` and `MONTH TO DATE`, but its current version can be an incomplete afternoon report; retain versions and issuance times for the Oct 7 rain contract.

## Execution economics and data feeds

- Polymarket uses a CLOB. Its [prices and orderbook documentation](https://docs.polymarket.com/concepts/prices-orderbook) says the displayed probability is normally the bid/ask midpoint, or the last trade if the spread exceeds 10¢. A buy pays the ask, and a sell receives the bid. The Gamma best quotes above are snapshots, not guaranteed fillable size; use the live order book and depth at decision time.
- Current [Polymarket fee documentation](https://docs.polymarket.com/trading/fees) sets **weather taker fees** to `shares × 0.05 × price × (1 − price)`, charged at matching; makers pay no trading fee. The example live high-temperature Gamma market reports `feesEnabled=true` and `feeSchedule={rate:0.05, exponent:1, takerOnly:true, rebateRate:0.25}`. At 50¢, the weather taker fee is 1.25¢ per share ($1.25 per 100 shares), before spread and any later sale. A 64¢ YES purchase costs another 1.152¢ per share in fee. Check market-specific fee parameters before applying a generic formula.
- Polymarket's [negative-risk documentation](https://docs.polymarket.com/concepts/negative-risk) says that, in a qualifying mutually exclusive group, one No token can be converted to Yes tokens for every other outcome. This makes cross-bracket price consistency worth monitoring, but an apparent sum-of-prices opportunity is not executable unless enough depth exists and fees, conversion, and leg risk are covered.
- Polymarket documents [market discovery via the public Gamma API](https://docs.polymarket.com/market-data/discover-markets) and [live CLOB market WebSocket books and price changes](https://docs.polymarket.com/market-data/realtime-data). The examples returned `version=v1` on these October weather contracts; the newer V2 schema in current documentation should not be assumed to apply to every active weather market.
- The [maker rebate program](https://docs.polymarket.com/programs/maker-rebates) allocates 25% of eligible weather taker fees among makers by their share of executed liquidity, with a $1 accrued payout threshold. The separate [liquidity rewards program](https://docs.polymarket.com/programs/liquidity-rewards) pays for qualified resting quotes subject to each market's minimum size, maximum spread, and reward allocation. In the snapshot, [NYC Oct 7 low](https://gamma-api.polymarket.com/events?slug=lowest-temperature-in-nyc-on-october-7-2026) reported reward settings on several bins, including 50–51°F at a configured $22 daily rate and 20-share minimum. This is a parameter to test, not an assured return; quote competition and adverse selection matter.

## Weather-data capabilities and pitfalls

- The [NWS public API](https://www.weather.gov/documentation/services-web-api) provides free forecasts, alerts, observations, hourly forecasts, and raw grid forecasts for U.S. locations, with rate limits and a required identifying User-Agent. Its March 2026 known issues state that station observations' 24-hour max/min may be null outside the Central time zone, observations may lag by up to 20 minutes, and precipitation values in observations can be rounded down to the nearest centimeter (amounts under 0.4 inch may appear as zero). This API is useful context, **not a replacement** for the weather contract's exact resolution page or CLI.
- NOAA's [Aviation Weather Data API](https://aviationweather.gov/data/api/) provides worldwide METARs and TAFs, up to 30 days of history, with current all-METAR cache files updated every minute and a 100-request/minute API limit. It can support station nowcasts and audit trails, subject to checking each contract's observation filtering and rounding against NOAA WRH.
- NWS describes the [HRRR](https://forecast.weather.gov/glossary.php?word=HR) as an hourly updated 3 km model. Its [weather-model overview](https://www.weather.gov/ilx/about_models) emphasizes combining models into probabilistic forecasts. These are candidate inputs for a calibrated station-level forecast, not themselves evidence of market mispricing.

## Edge hypotheses to test (none demonstrated yet)

1. **Station and rule matching.** Build a replay dataset of the exact settlement series for each station and contract rule. Test whether market participants systematically overuse city forecasts, non-settlement stations, all-report METAR highs/lows, or the wrong local-day boundary. The test must show a net gain over executable bid/ask and weather taker fees, not just prediction accuracy.
2. **Daily lows and rain.** Both are active and outside a high-temperature-only scope. Low-temperature events sometimes have thin books despite rewards; daily rain uses a sharp 0.01-inch CLI threshold and a specific publication cutoff. Separate models could exploit errors near those boundaries, but the observed 28¢ low-temperature spread and 96¢ Boston rain spread show why crossing quotes blindly would be costly.
3. **Late-day nowcasting.** Once the high/low bound or a CLI precipitation threshold is observed, some outcomes become impossible or nearly certain. Test quote response latency against source publication, special reports, and remaining intraday weather risk. Account for the fact that a high already reached cannot fall, while a low already reached cannot rise.
4. **Cross-bin consistency.** Screen mutually exclusive temperature/monthly precipitation events for underpriced complete sets or inconsistent tails using live depth, fee-aware prices, and negative-risk mechanics. Treat any resulting signal as hypothetical until simultaneous execution/hedging is demonstrated; thin-bin stale quotes can look like arbitrage.
5. **Maker economics.** On liquid temperature bins, test whether spread capture plus maker rebates/rewards exceeds adverse selection, queue nonfills, inventory risk, and capital use. Rewards alone should not drive orders into weak forecasts.
6. **Monthly accumulation.** Follow official Central Park month-to-date precipitation, forecast remaining rainfall as a distribution, and remove bins already excluded by accumulated totals. This has a longer horizon and possible Jan 2027 settlement, so evaluate return on tied-up capital.

## Repo implications / validation

- Represent each contract's station, source, unit, observed column, daily boundary, hourly-only filter, fallback, and correction window explicitly. The NYC daily rain, NYC daily temperature, and Amsterdam temperature rules above are materially different. Add new low-temperature or rain markets to paper discovery only after those semantics are implemented.
- A scan should compare a calibrated, complete probability distribution to **executable CLOB bid/ask and depth**, applying the market's actual fee schedule. Polymarket's displayed midpoint and Gamma outcome price do not establish attainable edge. Keep the individual provider values and their publication timestamps, so forecast disagreement and true data age can be measured.
- Reconstruct exact settlement labels and source timestamps; archive Gamma metadata plus live CLOB depth; produce station/day calibration; replay fees, stale quotes, size, queue, and settlement delays; then paper trade. A positive result should survive walk-forward dates and comparison with a simple market-implied baseline before considering live execution.

## Current bot and code audit

The checked-out bot discovers a fixed list of **daily high-temperature** event slugs, compares each bracket's Gamma outcome price with WU, Open-Meteo, Visual Crossing, NOAA, and WeatherAPI forecasts, then paper-trades gated signals. Its separate precipitation path targets **monthly total** buckets and is disabled by default. `paper_shadow` mirrors accepted paper trades into a simulated order/fill ledger; there is no real-money order path. See [scanner/weather_event_scanner.py](scanner/weather_event_scanner.py), [weather_bot/temperature.py](weather_bot/temperature.py), [precipitation/precip_scanner.py](precipitation/precip_scanner.py), [weather_bot/config.default.yaml](weather_bot/config.default.yaml), and [weather_bot/execution/base.py](weather_bot/execution/base.py).

The following are code-level reasons to distrust a raw displayed “edge” until corrected:

1. **The reported fair probability and reported edge disagree.** [Discrepancy selection](logic/discrepancy_logic.py#L137) averages the agreeing providers' discrepancies but stores the *first* provider's probability as `forecast_prob`. That value reaches the [shadow bid cap](weather_bot/execution/shadow_execution.py#L515). For two provider probabilities of 0.50 and 0.35 versus a 0.20 market, the output edge is 0.225 (mean fair value 0.425), but the cap uses 0.50. With a 0.12 edge floor, this permits a 0.38 bid instead of 0.305. The cap also needs actual fee and book costs.
2. **The dispersion gate hides some dissenting forecasts.** [_check_single_source](logic/discrepancy_logic.py#L33) removes every source within 0.10 of the market before [temperature dispersion](weather_bot/temperature.py#L159) is calculated. For 0.22/0.40/0.42 provider probabilities and a 0.20 market, the bot labels two agreeing YES sources with dispersion 0.02; the full-provider range is 0.20.
3. **Freshness is scan age, not forecast age.** The [freshness gate](weather_bot/strategy.py#L759) timestamps the newly created signal, while provider issue times are not carried through the [forecast snapshot](weather_bot/temperature.py#L183). A cached forecast can appear fresh to the strategy.
4. **Uncertainty and fees are misaligned with the contract.** The [temperature model](forecast/forecast_engine.py#L780) uses a fixed 2.5°F/1.5°C Gaussian standard deviation for every city, provider, and forecast lead time; no historical calibration is present in this checkout. Paper P/L uses a flat [50 bps fee](weather_bot/config.default.yaml#L30) on notional, while the current [weather taker formula](https://docs.polymarket.com/trading/fees) varies with price. At 50¢, 50 bps of trade notional is 0.25¢ per share versus a 1.25¢ weather taker fee per share. This can materially overstate paper P/L for taker fills.
5. **Book, station, and cluster checks come too late or are absent.** [Signal generation](parser/weather_parser.py#L49) uses Gamma `outcomePrices` before [shadow execution](weather_bot/execution/shadow_fill.py#L24) examines the CLOB; [station coordinates](forecast/forecast_engine.py#L741) are hardcoded by city instead of checked against each current event rule; the [entry gate](weather_bot/strategy.py#L261) caps positions per market but has no city/date/direction cluster cap or re-entry cooldown. These are research and risk-control priorities, not proof of a new edge.

The working branch fixes the signal probability inconsistency in item 1 by using the mean of agreeing provider probabilities for both `forecast_prob` and the reported edge. It also includes near-market providers in the dispersion used by the strategy gate, addressing item 2. Focused tests cover both changes and the exact 10-point source threshold. The fee and executable-book issues remain; paper and shadow P/L should not be read as net tradable edge.

The [May 15 handoff](WEATHER_BOT_HANDOFF_2026-05-15.md) reports about **−$29.56 total realistic shadow P/L** in its latest one-day bundle, mostly linked to future-date YES tails and correlated city/date losses. That is one old snapshot, not a current profitability estimate. This checkout has no `data/weatherbot.db` or recent analysis bundle; the only local database is an old weather cache. The local test suite passed **179 tests** using `uv run --no-project --with-requirements requirements.txt python -m pytest -q`; this verifies current tests, not forecast calibration or trading returns.

## Immediate credential remediation

The public repository still tracks `.env` even though `.gitignore` lists it. Its current public blob matches the local file, which contains populated `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, and `WU_API_KEY` entries. No values were displayed or used in this review. Treat the bot token and API key as exposed: revoke or rotate them at their providers, remove `.env` from Git tracking while preserving a local ignored copy, and consider history cleanup only after rotation and coordination with anyone using the repo. Removing the file from the latest tree alone does not invalidate copies already in Git history.

The working branch removes `.env` from Git tracking while retaining the local ignored file and adds a blank `.env.example`. A separate GitHub personal access token was visible inside Home Assistant's stored add-on repository URL in Supervisor logs; the token value is deliberately omitted here. Remove that credential-bearing repository URL and rotate the token. These rotations are required even after the files and URL are cleaned up, because prior Git history and logs may retain the old values.
